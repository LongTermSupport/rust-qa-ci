# rqaci_suppression_generated

Dylint lint in the bundled `rqaci_lints` library. Level: deny.

## What it flags

An `allow` or `expect` lint attribute that exists only after macro expansion and covers code the
caller wrote, when the macro that produced it is defined in the workspace (a local
`macro_rules!`, or a proc-macro crate whose sources are under the workspace root). Examples:

- a `macro_rules!` body that writes `#[$level(clippy::unwrap_used)]` and is invoked with `allow`;
- a macro that wraps the caller's item in `#[expect($lint, reason = "...")]` with a lint name the
  caller passes in;
- a workspace proc macro that emits a lint attribute over the tokens it was given.

The report points at the outermost macro invocation in your source.

It does not flag:

- attributes written literally in source, including literally inside a macro definition: those
  are `rqaci.suppression.unrecorded`'s, which already requires a project-record exception;
- attributes that cover only code the macro itself generated (nothing you wrote is silenced);
- attributes produced by compiler desugarings (`?`, `for`, `async`), the standard library, or
  dependency macros from the registry or git (`serde`, `thiserror` and the like): those are the
  dependency author's lint levels, outside the project's suppression policy, like the
  dependency's own source.

## Why

The suppression guard reads source text. A macro can assemble a lint attribute from fragments,
so the text never contains a lint attribute the guard can read, yet after expansion the compiler
silences the lint over the caller's code. That is a suppression with no recorded decision, which
is exactly what the project record exists to prevent.

## How to fix correctly

1. Fix the code inside the invocation so the lint passes, and stop the macro from emitting the
   attribute (let callers write their own, literal, recorded `expect` when they need one).
2. If a workspace macro genuinely must emit the attribute, write it literally in the macro body
   (for example a fixed `expect(dead_code, reason = "...")` rather than `$level(...)`), so the
   suppression guard sees it and requires its record exception.
3. As a last resort, accept one site: put an expectation for this lint on the nearest enclosing
   item you write, gated on the library, and record it in the project record (rule
   `rqaci_suppression_generated`, the file's path):

   ```rust
   #[cfg_attr(
       dylint_lib = "rqaci_lints",
       expect(rqaci_suppression_generated, reason = "generated by the vendored table! macro; fix tracked upstream")
   )]
   mod tables {
       table!(allow, /* ... */);
   }
   ```

## Why rustc, not syntax

The attribute does not exist in the source text, only in the compiler's expanded program, so no
syntactic rule can see it. The lint walks rustc's post-expansion HIR attribute map, uses hygiene
data (which macro produced each token, and where that macro is defined) to separate workspace
macros from dependencies and desugarings, and walks the attributed node to decide whether any
caller-written item, field or expression is covered. It needs no type information beyond that.

## Limits

A dependency macro that passes a caller's level through unchanged (`dep_macro!(allow, ...)`) is
attributed to the dependency. Workspace proc-macro crates are recognised by their source path
being under the build's working directory and outside `CARGO_HOME`, `CARGO_TARGET_DIR` and
`target/`; vendored dependency sources inside the workspace count as workspace code.

## Suppression

Only as in step 3: `#[expect]`, gated on `dylint_lib = "rqaci_lints"`, plus a matching
exception in the project record. The report is emitted on the parent of the attributed node, so
a generated attribute cannot silence the report about itself.
